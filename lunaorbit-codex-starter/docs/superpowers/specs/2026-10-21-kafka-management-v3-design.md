# Kafka 完整管理 v3 设计

日期：2026-10-21。状态：用户已确认书面设计并要求继续实施；第1批已完成并在授权实验环境验收，见开发日志。其余批次尚未实施。

## 目标与范围

LunaOrbit 提供完整的 Kafka 集群资源管理，以应用作为账号、原生 ACL 和配额的日常入口。新增账号采用 SCRAM-SHA-256；支持已有账号、密码的主动录入及安全托管。原生规则不能因为未归属应用而被隐藏。Kafka 使用 franz-go，MM2 配置管理继续仅走已有 Kite 契约，不引入 GitOps。禁止访问生产；真实验证仅在已授权隔离实验环境执行。

交付分四批，每批验收后停止：

1. SCRAM 账号、凭据托管、已有账号录入、应用关联、原生 ACL 融合。
2. Topic/Broker 完整配置、Topic 生命周期及副本重分配。
3. 消费组/Offset、消息查询与受控生产、配额。
4. 综合故障、多 Broker、兼容性及管理体验验收。

当前实施范围为第1批。配额等后续能力不得显示为已实现，也不提前增加空壳页面。

## 方案选择

- 推荐：独立账号实体 + 应用关联 + Kafka 原生规则。允许一个应用多个账号和一个账号关联多个应用，账号生命周期独立，匹配既有集群。
- 不采用应用直接持有唯一用户名/密码：无法表达共享账号、迁移账号及未归属身份。
- 不另设割裂的 ACL 主菜单：统一模块内提供应用、全部账号、全部规则三个视图；资源详情跳转至同一规则界面。

## 数据模型

账号以 registration_id + username 唯一，机制固定 SCRAM-SHA-256。账号与 Kafka Principal 分开记录，默认生成 User:<username>，不能将 LDAP 身份或负责人文本推导为 Kafka Principal。自定义 Principal 映射必须显式配置并验证，未知映射不声称授权已验证。

Application 保留名称、负责人、用途和修订；移除应用必须只能使用一个不可变 Principal 的约束，改用 ApplicationAccount 关联。迁移旧 Application.Principal 至已有身份账号及关联，不创建认证凭据、不改现有 ACL；同集群同身份合并，保留历史变更单快照兼容。无法可靠推导用户名的旧 Principal 标记为仅身份资料，等待显式绑定。

Account 保存ID、所属登记、username、principal、mechanism、管理来源、凭据托管状态、最近观察状态、revision；不保存明文密码。来源区分平台创建、人工关联、Kafka发现。身份观察失败不自动当作身份删除。

AccountSecretVersion 保存加密内容或Secret引用、加密密钥版本、账号/集群绑定、时间与revision；不能进入普通账号JSON、变更预览、审计或前端持久化缓存。ApplicationAccount 记录关联并禁止重复。

ProvisionOperation 保存逐步进度、申请/审批/执行人、幂等键、修订、指纹及安全结果码；密码不进入操作快照。主密钥独立于数据库，通过服务端配置或外部SecretProvider注入；持久化模式没有有效主密钥时拒绝启用凭据托管。

## 创建与录入流程

新建应用选择集群、用途与资源权限后提交，后端生成用户名与高强度随机密码。先保存加密待开通凭据和操作记录，再创建 SCRAM、配置 ACL、验证认证及回读结果，全部通过后才标记就绪。Kafka写保持原受限网络工厂、超时及默认禁写；只有明确配置的实验目录目标允许真实写。

创建前检查身份是否存在；存在则要求关联，不进行upsert覆盖。Kafka SCRAM写本身没有创建专用CAS，因此平台锁不能防止外部管理员同时创建同名身份。生成随机唯一用户名并在写前再次检查；记录此并发边界，禁止把Kafka原生upsert描述为原子create-only。

已有账号支持：用户名+密码验证成功后托管；仅用户名关联并标记未托管；从Kafka发现后关联应用。录入密码不写Kafka、不改原密码、不自动变更ACL。失败只返回分类错误，不回显凭据。

流程部分失败必须保留逐步结果。重试读取原操作和已完成步骤，不重新生成密码或无条件重建账号。超时/断连后先核验，不自动重放凭据写。若既有身份与待开通记录不一致，进入人工复核，不能自动覆盖或删除。

## 密码交付与安全约束修订

用户要求支持查看平台托管的密码。因此新增受控凭据读取例外，覆盖旧 SECURITY.md 和 KAFKA_CLUSTER_MANAGEMENT.md 的笼统禁止回传表述：仅应用业务账号的托管密码可通过独立POST操作、独立权限和审计查看；平台连接集群的管理密码、LDAP密码、Kite Key不在例外内。

普通列表/详情永不返回密码。查看接口响应Cache-Control:no-store，并禁止写入日志、Trace、URL、localStorage、sessionStorage、持久化前端状态或通用导出。前端默认遮蔽，显式显示/复制，关闭即清除。审计只记操作者、目标、时间与动作，不记正文。查看权限与账号管理/ACL管理分离，Topic范围授权不能推导出查看密码权限。

仅对已生成或录入并托管的密码提供查看。Kafka SCRAM描述接口不返回原始密码；未托管身份明确显示未托管。Kafka账号存在、托管密码可解密不等于密码仍有效；外部改密后认证核验失败，应显示不一致，不自动覆盖外部密码。

第1批交付生成、录入、查看与验证。原账号改密/删除及双账号迁移必须有完整影响预览、权限、审批和恢复语义才开放；未实现时明确禁用，不能做无审批的重置捷径。相同用户名相同SCRAM机制不存在两套独立密码并行窗口。

## 原生 ACL

统一完整表达 Principal、Host、ResourceType、ResourceName、PatternType、Operation、Permission。资源包括Topic、Group、Cluster、TransactionalId、DelegationToken；有效操作组合由后端能力表约束。精确、前缀、通配符与ALLOW/DENY按Kafka真实语义处理。

生产/消费/事务/幂等模板只生成可查看的原生规则。消费要求Topic与Group；不会默认授予集群ALL或创建Topic。高级规则支持Broker实际可用的组合，相关能力不足时明确禁用。

全部规则视图包括外部规则及未归属Principal。外部规则只有显式选择后才能修改/删除，精确删除匹配所有字段。变更预览区分新增、已存在、删除、保留；使用当前规则指纹与修订，执行前及每步重新检查资源范围和写开关。列表分页/过滤必须先做权限过滤再分页，不能通过详情、计数或跨范围规则泄漏。

应用模板与已有按资源范围授权保留。Cluster等非Topic/Group规则要求明确的相应集群级权限，不能通过空资源名绕过范围检查。密码读取与SCRAM变更要求不受Topic/Group前缀限制的账号权限。

## UI 与平台权限

保留现有管理平台布局。应用与权限内：应用列表/详情、全部账号、全部规则。应用详情展示账号、来源、托管/认证状态、实际规则、共享应用及操作记录。新建采用应用资料→新建/关联账号→选择权限→差异预览→提交→逐步结果；不把账号创建、ACL写和回读混成单一成功提示。

原团队授权移至平台访问控制，描述平台用户/可信LDAP组可访问的集群和管理动作。Kafka业务账号与平台身份彻底分开。默认独立审批；实验自动批准只按既有admin-lab开关启用，记录实际操作者。拒绝浏览器自报角色/组。

## 后续三批设计边界

第2批：配置查询展示生效值、source、敏感性、read-only、synonyms及可取得的默认值；未知默认不猜测。增量设置或删除覆盖表达恢复继承，写入前校验有效类型/范围与目标能力。静态配置只说明需重启，不自动重启Broker。Topic删除/副本重分配采用异步操作、影响预览、独立授权与回读，跟踪节流及取消边界。

第3批：消费组成员/分配/位点/Lag，重置明确按时间/最早/最新/指定Offset预览及组状态前置条件；消息分页有条数/字节/时间上限，单独内容权限，不默认保存消息体；受控生产审计不存敏感payload。配额按user/client-id及组合查询和增量调整，区分来源与默认。

第4批：多Broker故障、外部漂移、重启、操作中撤权、跨版本及性能验收；没有实际监控时不伪造容量/健康。已有MM2边界与证据状态保持。

## 实施与验证文件边界

扩展 backend/internal/kafkaadmin 原生SCRAM适配和受限凭据验证；新增业务账号/SecretProvider模块；registry增加动作授权；workspace保留并迁移应用与ACL快照。新增顺序数据库迁移，更新server装配与配置，前端增加账号/完整规则组件，移交团队入口。旧接口在过渡期保留鉴权和兼容，不由前端直连Kafka。

验证必须包含：Go全量test/vet；前端test/typecheck/lint/build；PostgreSQL迁移幂等、旧资料升级、加密落库和重启；已有账号录入不改密；同名冲突；重复提交；部分失败与超时；秘密不进入响应/审计/日志；角色/范围/撤权矩阵；真实浏览器开通和密码查看。

实验必须从ANONYMOUS superuser的ACL CRUD升级为真正SCRAM-SHA-256 listener。使用合成管理身份和受限业务身份，实际验证正确/错误密码、允许/拒绝的Topic生产消费、Group范围、精确/前缀/DENY/撤权；管理连接与业务核验连接分离。MM2现有链路须恢复且合成消息复制通过，禁止为测试破坏其他profile或生产资源。

第1批完成需可从浏览器添加应用并开通真实账号与所选ACL，安全查看托管密码，录入已有账号不改变原身份和规则，全部账号/规则可查询与明确管理，跨用户范围不越权，重启保留数据。未实测的兼容/企业LDAP/生产KMS必须列为未验证。更新路线图和日志后停止，不自动开始第2批。
